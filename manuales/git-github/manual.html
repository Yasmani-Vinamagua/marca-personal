Fundamentos del control de versiones

Conceptos esenciales

Un sistema de control de versiones registra los cambios realizados sobre un conjunto de archivos a lo largo del tiempo, de modo que sea posible consultar versiones anteriores, comparar cambios y colaborar sin sobrescribir el trabajo de otras personas. Git es un sistema de control de versiones distribuido: cada copia del proyecto contiene el historial completo. GitHub es un servicio en línea que aloja repositorios Git y añade herramientas de colaboración, como las solicitudes de extracción y los issues.

Estados y áreas de trabajo

Un archivo versionado puede hallarse en uno de tres estados: modificado (cambiado, pero no registrado), preparado (marcado para formar parte del próximo commit) o confirmado (almacenado de forma segura en la base de datos local). A estos estados corresponden tres áreas: el directorio de trabajo, el área de preparación (staging area o índice) y el directorio de Git (Chacon y Straub, 2014).

Para ampliar

El área de preparación es un archivo, generalmente ubicado en el directorio de Git, que almacena la información de lo que formará parte del próximo commit; su nombre técnico es «índice» (Chacon y Straub, 2014).

Síntesis

  • Git registra el historial del proyecto como una secuencia de commits.
  • Los cambios fluyen del directorio de trabajo al área de preparación y de allí al repositorio.
  • GitHub aloja repositorios y facilita la colaboración, pero Git funciona sin él.

Configuración inicial

Identidad y editor

La configuración inicial se realiza una sola vez por equipo con el modificador --global. El nombre y el correo quedan asociados a todos los commits.

git config --global user.name "Nombre Apellido"
git config --global user.email "correo@dominio.com"
git config --global core.editor "code --wait"
git config --global init.defaultBranch main

La última instrucción establece main como rama predeterminada de los repositorios nuevos, y la tercera configura Visual Studio Code como editor.

Importante

En los comandos deben emplearse comillas rectas ("), no tipográficas (“ ”). Las comillas tipográficas, frecuentes al copiar texto desde procesadores de texto o notas, provocan errores o valores incorrectos.

Finales de línea y consulta de la configuración

Windows y macOS/Linux utilizan finales de línea distintos. El valor core.autocrlf permite normalizarlos: true en Windows e input en macOS y Linux.

git config --global core.autocrlf true      # Windows
git config --global core.autocrlf input     # macOS / Linux

Flujo básico de trabajo

Creación del primer repositorio

El procedimiento parte de una carpeta de proyecto vacía:

  1. Abrir la terminal y crear la carpeta del proyecto (mkdir proyecto1).
  2. Ingresar a la carpeta (cd proyecto1) y comprobar la ubicación con pwd.
  3. Inicializar el repositorio con git init.
  4. Verificar que se creó la carpeta oculta .git con ls -al.
  5. Crear un archivo de texto y guardarlo en la carpeta.

Registro de cambios

El ciclo básico consiste en comprobar el estado, preparar los cambios y confirmarlos con un mensaje descriptivo.

git status                       # estado de los archivos
git add nombre_archivo.txt       # prepara un archivo
git add .                        # prepara todos los cambios
git commit -m "Mensaje"          # confirma lo preparado
git commit -am "Mensaje"         # prepara y confirma archivos ya rastreados
Consejo

Si se ejecuta git commit sin el modificador -m, Git abre el editor configurado para redactar el mensaje. Si el editor es Vim, se guarda y se sale con Esc seguido de :wq (o Shift + Z Z).

Eliminación de archivos

El comando git rm nombre_archivo.txt elimina el archivo del directorio de trabajo y lo retira del seguimiento. Con git rm --cached nombre_archivo.txt el archivo deja de rastrearse, pero se conserva en el disco, lo que resulta útil cuando se añadió por error un archivo que debía ignorarse.

Revisión del contenido y del historial

cat nombre_archivo.txt           # muestra el contenido
code nombre_archivo.txt          # abre el archivo en el editor
git log nombre_archivo.txt       # historial del archivo
git log --oneline                # historial compacto
git log --stat                   # archivos modificados en cada commit

Exclusión de archivos con .gitignore

El archivo .gitignore enumera los patrones de archivos que Git no debe rastrear. Se crea en la raíz del proyecto y se versiona como cualquier otro archivo.

node_modules/
*.log
dist/
.env

Cada línea excluye, respectivamente, una carpeta completa, todos los archivos con una extensión, las carpetas de compilación y las variables de entorno.

Importante

Los secretos (contraseñas, claves de API, archivos .env) no deben subirse nunca a un repositorio. Si se añadió un archivo antes de incluirlo en .gitignore, debe retirarse del seguimiento con git rm --cached (DevTalles, s. f.).

Síntesis

  • El ciclo básico es status → add → commit.
  • git rm --cached detiene el seguimiento sin borrar el archivo.
  • .gitignore evita versionar archivos generados o confidenciales.

Inspección del historial

Comparación de cambios

git diff                         # cambios aún sin preparar
git diff --staged                # cambios ya preparados
git diff rama1..rama2            # compara dos ramas
git diff <commit_reciente> <commit_antiguo>   # compara dos commits
git show <commit>                # cambios introducidos por un commit
git show <commit>:archivo        # archivo tal como estaba en ese commit

Historial y autoría

git log --oneline --graph --all  # historial gráfico de todas las ramas
git log -p                       # historial con el diff de cada commit
git log --author="nombre"        # commits de una persona
git log -- <archivo>             # commits que tocaron un archivo
git shortlog -sn                 # número de commits por persona
git blame <archivo>              # autor y commit de cada línea
git blame <archivo> -L35,50      # solo las líneas 35 a 50

La opción git shortlog -sn --all incluye las ramas no fusionadas, y --no-merges excluye los commits de fusión.

Deshacer cambios y recuperar versiones

Descartar cambios en archivos

git restore <archivo>            # vuelve al último commit
git restore --staged <archivo>   # saca el archivo del stage sin perder cambios
git restore .                    # descarta todos los cambios sin guardar
git checkout <commit> <archivo>  # muestra cómo era el archivo en ese commit
git commit --amend -m "nuevo mensaje"   # corrige el último commit
Importante

git restore . descarta de forma irreversible los cambios no confirmados. Conviene revisar git status y git diff antes de ejecutarlo.

Reset y revert

El comando git reset mueve la rama actual a otro commit; según el modificador, conserva o descarta el trabajo posterior. En cambio, git revert crea un commit nuevo que invierte los efectos de otro, por lo que es la opción segura cuando los commits ya se compartieron.

Tabla 4Variantes de git reset

ComandoEfecto
git reset --soft HEAD~1Deshace el último commit y conserva los cambios en el stage.
git reset --mixed HEAD~1Deshace el commit y deja los cambios sin preparar (comportamiento predeterminado).
git reset --hard <commit>Regresa a ese commit y descarta todo lo posterior, incluido el stage.
git revert <commit>Crea un commit que revierte otro; adecuado para repositorios compartidos.

Nota. Adaptado de Vega (2021) y DevTalles (s. f.).

Recuperación con reflog

El comando git reflog registra los movimientos de HEAD, incluso los commits que ya no son alcanzables desde ninguna rama. Permite volver al estado en que el proyecto funcionaba:

git reflog                       # lista el hash y la posición de HEAD
git reset --soft <hash>          # vuelve conservando lo que hay en staging
git reset --hard <hash>          # vuelve descartando todo, incluido el staging

Limpieza de archivos sin seguimiento

git clean --dry-run              # muestra qué se borraría
git clean -f                     # borra los archivos listados
git clean -fd                    # borra también carpetas
Importante

Los archivos eliminados con git clean no pueden recuperarse desde Git. Debe ejecutarse siempre primero con --dry-run.

Síntesis

  • restore descarta cambios en archivos; reset mueve la rama; revert añade un commit inverso.
  • --hard y clean son destructivos: deben usarse con verificación previa.
  • reflog permite recuperar commits aparentemente perdidos.

Ramas y fusión

Gestión de ramas

Una rama permite desarrollar una funcionalidad o corregir un error sin alterar la línea principal. La práctica recomendada es una rama por funcionalidad o error, evitando trabajar directamente en la rama principal (DevTalles, s. f.).

git branch                       # lista las ramas (* indica la actual)
git switch -c <rama>             # crea una rama y se mueve a ella
git switch <rama>                # cambia de rama
git checkout -b <rama>           # equivalente clásico de switch -c
git merge <rama>                 # fusiona la rama indicada en la actual
git branch -d <rama>             # elimina una rama ya fusionada
git branch -D <rama>             # fuerza la eliminación
git branch -m <nuevo-nombre>     # renombra la rama actual
git show-branch --all            # historia de todas las ramas
gitk                             # visualización gráfica
Nota

Para fusionar, el procedimiento consiste en situarse en la rama que recibirá los cambios (git switch main) y ejecutar git merge <rama>.

Resolución de conflictos de fusión

Cuando dos ramas modifican la misma línea, Git no puede decidir cuál conservar y marca el conflicto en el archivo:

<<<<<<< HEAD
versión de la rama actual
=======
versión de la rama entrante
>>>>>>> otra-rama
  1. Editar el archivo y dejar el contenido final, eliminando los marcadores.
  2. Marcar el conflicto como resuelto con git add <archivo>.
  3. Cerrar la fusión con git commit.
  4. Para cancelar el proceso: git merge --abort.

Tabla 5Opciones de Resolución de Conflictos en el Editor

OpciónEfecto
Accept Current ChangeConserva la versión de la rama actual (HEAD) y descarta la entrante.
Accept Incoming ChangeAcepta los cambios de la rama que se fusiona.
Accept Both ChangesUne ambas versiones; exige revisar que el resultado sea coherente.
Compare ChangesAbre una comparación visual para decidir línea por línea.

Nota. Opciones del editor Visual Studio Code. Adaptado de Vega (2021).

Reorganización y selección de commits

git rebase main                  # coloca los commits de la rama sobre main
git rebase -i HEAD~3             # rebase interactivo: squash, reword, edit
git cherry-pick <commit>         # trae un commit concreto a la rama actual
Importante

No debe aplicarse rebase a commits ya publicados en un remoto compartido, pues reescribe el historial y afecta a quienes trabajan sobre él (DevTalles, s. f.).

Trabajo a medias: stash y worktree

El comando git stash guarda temporalmente los cambios en curso y deja el directorio limpio, de modo que pueda cambiarse de rama.

git stash                        # guarda los cambios en curso
git stash list                   # lista los stashes
git stash pop                    # recupera el último y lo elimina de la lista
git stash apply                  # lo recupera y lo conserva
git stash branch <nueva_rama>    # crea una rama a partir del stash
git stash drop                   # elimina el último stash

Como alternativa, git worktree add ../hotfix <rama> abre otra rama en una carpeta distinta sin tocar el trabajo actual; se retira con git worktree remove ../hotfix.

Síntesis

  • Las ramas aíslan el trabajo; merge lo integra.
  • Un conflicto se resuelve editando, preparando y confirmando.
  • stash y worktree permiten cambiar de contexto sin perder trabajo.

Repositorios remotos y GitHub

Conexión y sincronización

git remote add origin <url>      # conecta el repositorio local con el remoto
git remote -v                    # lista remotos (fetch y push)
git push -u origin main          # sube la rama y la vincula (primera vez)
git push                         # sube los commits
git pull                         # descarga y fusiona cambios del remoto
git pull --rebase                # descarga y reaplica los commits propios encima
git fetch                        # descarga sin fusionar
git clone <url>                  # descarga un repositorio con su historial
git clone --depth 1 <url>        # clon superficial: solo el último commit

Si el repositorio remoto y el local se crearon por separado y tienen historiales sin relación, git pull origin <rama> --allow-unrelated-histories obliga a fusionarlos. Para consultar las ramas remotas se emplea git branch -r, y git branch -a muestra las locales y las remotas.

Importante

El nombre de la rama debe coincidir en el repositorio local y en GitHub. Los apuntes originales emplean master; en repositorios actuales lo habitual es main. Conviene verificar el nombre con git branch antes de ejecutar push o pull.

Autenticación con claves SSH

Las claves SSH permiten comunicarse con GitHub sin introducir credenciales en cada operación. El procedimiento general es el siguiente:

  1. Generar el par de claves (pública y privada) con ssh-keygen.
  2. Iniciar el agente y agregar la clave privada (eval "$(ssh-agent -s)" y ssh-add <ruta_de_la_clave>).
  3. Copiar el contenido de la clave pública (archivo .pub) y pegarlo en GitHub, en Settings → SSH and GPG keys.
  4. Cambiar la dirección del remoto a la versión SSH: git remote set-url origin <direccion_SSH>.
  5. Verificar con git remote -v y sincronizar con git pull.
Para ampliar

GitHub recomienda generar la clave con el algoritmo Ed25519: ssh-keygen -t ed25519 -C "correo@dominio.com". El comando ssh-keygen -t rsa -b 4096 -C "correo@dominio.com", empleado en los apuntes, queda reservado para sistemas antiguos que no admiten Ed25519 (GitHub, s. f.-b). En ese caso la clave privada se denomina id_rsa y la pública id_rsa.pub.

Si la conexión por el puerto habitual falla (por ejemplo, por restricciones de red), puede configurarse GitHub sobre el puerto 443 añadiendo al archivo ~/.ssh/config:

Host github.com
  Hostname ssh.github.com
  Port 443

Publicación con GitHub Pages

GitHub Pages publica contenido estático (HTML, CSS y JavaScript) directamente desde un repositorio. El procedimiento es el siguiente:

  1. Crear un repositorio en GitHub y clonarlo localmente.
  2. Añadir un archivo index.html, confirmar los cambios y subirlos.
  3. En el repositorio, abrir Settings → Pages, y en Build and deployment seleccionar Source → Deploy from a branch, elegir la rama y la carpeta (raíz o /docs) y guardar.
  4. Acceder a la dirección publicada desde el navegador.
Para ampliar

Además de «Deploy from a branch», GitHub ofrece publicar mediante GitHub Actions, opción indicada cuando se utiliza un proceso de compilación distinto de Jekyll o no se desea una rama dedicada a los archivos compilados (GitHub, s. f.-a). Los apuntes originales mencionan el nombre nombre_de_usuario.github.io para el repositorio del sitio personal.

Síntesis

  • push envía commits al remoto; pull los trae y fusiona; fetch solo los descarga.
  • Las claves SSH evitan introducir credenciales en cada operación; solo se comparte la clave pública.
  • GitHub Pages publica sitios estáticos desde una rama.

Colaboración en GitHub

Flujo de trabajo con ramas de funcionalidad

  1. Actualizar la rama principal con git pull.
  2. Crear la rama: git switch -c mi-funcionalidad.
  3. Trabajar y confirmar los cambios (git commit -am "mensaje").
  4. Subir la rama: git push -u origin mi-funcionalidad.
  5. En GitHub, abrir un pull request con la rama principal como base y la rama creada como comparación.
  6. Atender la revisión y las correcciones hasta obtener la aprobación.
  7. Si no hay conflictos, fusionar el pull request (Merge pull request) y eliminar la rama.
  8. Actualizar localmente: git switch main y git pull.

Contribución a proyectos ajenos

  1. Realizar un fork, que copia el repositorio a la cuenta propia.
  2. Clonar el fork: git clone <url-de-tu-fork>.
  3. Crear una rama, realizar los cambios y subirlos al fork.
  4. Abrir un pull request hacia el repositorio original.

Para mantener el fork actualizado se conecta el repositorio original como remoto upstream:

git remote add upstream <url-original>
git fetch upstream
git merge upstream/main
git push origin main

Etiquetas (tags)

Uso de etiquetas

Las etiquetas marcan un commit específico, habitualmente para señalar versiones publicadas. La etiqueta anotada es la recomendada, pues almacena autor, fecha y mensaje.

git tag                                   # lista las etiquetas
git tag -a v1.0.0 -m "Versión 1.0.0"      # crea una etiqueta anotada
git tag -a v0.9.0 <id_del_commit>         # etiqueta un commit anterior
git show-ref --tags                       # etiquetas con su commit
git push origin --tags                    # publica las etiquetas
git tag -d v1.0.0                         # elimina una etiqueta local
git push origin :refs/tags/v1.0.0         # elimina la etiqueta en el remoto

Síntesis

  • Las etiquetas anotadas señalan versiones y se publican de forma explícita con push --tags.
  • Eliminar una etiqueta local no la elimina en el remoto.

Para ampliar

Según la especificación, fix corresponde a una versión de parche y feat a una versión menor en el versionado semántico; un cambio incompatible, indicado con ! antes de los dos puntos o con la nota BREAKING CHANGE:, corresponde a una versión mayor (Conventional Commits, s. f.).

Recomendaciones de uso

  • Realizar commits pequeños y frecuentes, con mensajes claros redactados en modo imperativo.
  • Trabajar en una rama por funcionalidad o error; no hacerlo directamente en la rama principal.
  • Ejecutar git pull antes de comenzar para reducir conflictos.
  • Revisar git diff antes de cada commit.
  • Mantener un README y un .gitignore desde el inicio del proyecto.

Síntesis

  • Un mensaje estructurado facilita la lectura del historial y la automatización de versiones.
  • Los commits pequeños, las ramas por tarea y la revisión previa reducen errores y conflictos.

Productividad: alias y GitHub CLI

Alias

Un alias abrevia un comando largo. Pueden definirse en Git o en la terminal:

git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all"
git config --global --list                # revisa alias y ajustes globales
alias grafo="git log --all --graph --decorate --oneline"   # alias de la terminal

Con la primera línea, git st equivale a git status; con la segunda, git lg muestra el historial gráfico en una línea por commit. Entre los alias más habituales figuran co (checkout), br (branch) y ci (commit) (DevTalles, s. f.).

Bloques de código, tablas y avisos

Tres comillas invertidas seguidas del nombre del lenguaje activan el resaltado de sintaxis. Las tablas se construyen con barras verticales y una fila de guiones que separa el encabezado; los dos puntos en esa fila (:---, :--:, ---:) controlan la alineación. GitHub también admite avisos con las etiquetas [!NOTE], [!TIP], [!IMPORTANT], [!WARNING] y [!CAUTION] dentro de una cita en bloque (DevTalles, s. f.).

Consejo

Debe dejarse una línea en blanco entre párrafos; de lo contrario, se unen en uno solo. Para forzar un salto de línea sin nuevo párrafo se termina la línea con dos espacios. Conviene previsualizar el resultado antes de guardar.

Síntesis

  • Markdown permite documentar proyectos con una sintaxis mínima.
  • El README.md es la portada del repositorio.

Glosario

Alias. Abreviatura personalizada de un comando.

Área de preparación (staging area). Zona donde se agrupan los cambios que formarán parte del próximo commit.

Commit. Instantánea del proyecto guardada en el repositorio.

Conflicto de fusión. Situación en que dos ramas modifican las mismas líneas y Git no puede combinarlas automáticamente.

Fork. Copia de un repositorio ajeno en la propia cuenta de GitHub.

HEAD. Apuntador al commit o rama de trabajo actual.

Origin. Nombre por defecto del remoto principal.

Pull request. Solicitud de fusión de una rama, sujeta a revisión.

Rama (branch). Línea de trabajo paralela e independiente.

Remoto. Copia del repositorio alojada en un servidor.

Stash. Almacén temporal de cambios en curso.

Tag (etiqueta). Marca asociada a un commit, usada para señalar versiones.
